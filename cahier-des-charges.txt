1. EN BREF
====================================================================================================

Principe directeur du cahier : « zéro lead oublié ». Le CRM guide un télépro-commercial de la réception du
lead jusqu'à la vente, puis crée le client dans le CRM principal. Trois rôles : admin, manager, télépro.

Ce qui fonctionne aujourd'hui, de bout en bout, sur la base de DEV (crm-pose-dev) :
  - un lead arrive (Pabbly, Meta, formulaire, script de test) → il est enregistré, nettoyé, dédoublonné ;
  - le moteur l'attribue à un télépro éligible (ou le met en file tampon, avec le motif) ;
  - le télépro est alerté (son, barres, cloche), le voit dans « Ma journée », l'appelle ;
  - il déclare le résultat (pas de réponse, rappel, intéressé, documents, clôture) : le CRM calcule et
    programme la prochaine action, historise tout, et affiche le client suivant ;
  - l'administrateur configure utilisateurs, équipes, campagnes, règles d'attribution, et lit le Journal.

Ce qui reste : la conversion en vente et la transmission au CRM
principal, le pilotage (cockpit manager, équipe, rapports), les traitements serveur planifiés, la mise en
production, puis les évolutions (SMS, email, OCR, vente à distance, hub d'intégrations).

Qualité : 1125 tests unitaires (56 fichiers) ; typecheck de l'application, des fonctions Netlify et des
fonctions Firebase ; build de production OK.

====================================================================================================
2. DÉCISIONS PRISES
====================================================================================================

  - Application séparée : Lead/ (Vite + React 18 + TypeScript + Tailwind + Firebase 10 + Vitest), port 5180.
    Sidebar et connexion repris du CRM principal.
  - Même base Firebase que le CRM principal : DEV = crm-pose-dev, RÉEL = crm-label-pose. On repart de zéro
    (aucune donnée de l'ancien CRM Leads migrée pour l'instant). Collections préfixées « cl_ ».
  - Mêmes comptes et mêmes rôles que le CRM principal : le rôle vient de users/{uid}.role (administrateur,
    manager, télépro). Aucun rôle « Commercial » séparé (cahier §2).
  - Tests unitaires écrits avec le code. Toute la logique métier est en fonctions pures (moteur, ingestion,
    qualification, alertes, priorité, statuts), partagées entre navigateur et serveur.
  - Écritures d'administration (utilisateurs, équipes, campagnes, règles) : directement depuis le navigateur,
    protégées par les règles Firestore. Les fonctions Firebase correspondantes restent en secours.
  - Écritures « métier » sensibles : par des FONCTIONS NETLIFY, pas par les règles Firestore (le télépro n'a
    aucun droit d'écriture direct sur un lead). Raison : un résultat d'appel clôt une action, arrête un SLA,
    déplace des compteurs et écrit un historique immuable, ce que les règles ne peuvent pas prouver ; et
    l'utilisateur n'a pas les droits pour déployer des Cloud Functions Firebase.
      /api/leads          réception des leads (secret partagé, comme le CRM principal)
      /api/qualify-call   résultat de fin d'appel (jeton Firebase du télépro)
      /api/set-status     statut Disponible / Pause (jeton Firebase)
  - Développement local : `npm run dev` suffit (un plugin de dev sert /api/* avec les mêmes fonctions).
  - Droits appliqués par les règles Firestore (liste de leads cadrée par rôle), pas seulement par l'écran.

4. ÉCARTS ENTRE LE PLAN INITIAL ET LA RÉALITÉ
